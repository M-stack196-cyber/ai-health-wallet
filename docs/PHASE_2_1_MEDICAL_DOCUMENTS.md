# Phase 2.1 — Medical document management

Implemented against `docs/AI_Health_Wallet_Final_SRS_v3.docx` (v3.0), including FR-004–FR-010, UC-02/UC-03, security/validation sections 14.1–14.2, and acceptance cases V-02–V-04 and V-07–V-08. This phase implements original-file upload, private storage, ownership, metadata, filtering and retrieval. It does not run OCR, extract medical text, interpret records, or start processing jobs.

## Specification and database decisions

- Supported originals: PDF, JPG, JPEG and PNG. The uploaded original bytes are retained without conversion.
- New uploads require `category` and `hospital_name`; `document_date` is optional when unknown. Upload time is generated by PostgreSQL. Stored categories are the existing constrained values `lab_report`, `prescription`, `other_medical_document`.
- The SRS describes hospital metadata, but the existing `hospital_name` column is nullable. New API writes enforce its presence; existing nullable records remain readable. No backfill or schema change was necessary.
- The existing `medical_documents` table supplies UUID identity, patient FK, private bucket/key, original filename, file type, category, hospital, document date, upload timestamp and processing state. New rows use the existing `processing` state. That state does not indicate an OCR worker is running: processing is a later phase.
- Existing patient/category/hospital/upload/timeline indexes are reused. There is no migration, new table, grant or role change. Applied `0001_initial_schema.sql` is unchanged.
- The table has no metadata edit timestamp or edit-history log. PATCH preserves immutable upload time, filename, type, ownership, storage reference and processing state. This phase does not claim to provide a complete edit audit trail.
- CFG-03 upload/resource values require production approval; the defaults below are bounded development values. CFG-12 retention/deletion rules remain unresolved. No permanent DELETE endpoint or cascade deletion was added.

## API

Every endpoint requires the existing patient bearer JWT. Ownership always comes from its verified subject, never a request field. Document responses omit patient IDs, bucket names and object keys. Responses use `Cache-Control: no-store`.

| Method | Route | Behavior |
| --- | --- | --- |
| POST | `/api/v1/documents` | One multipart `file`, required category and hospital, optional document date; 201 only after storage and metadata succeed |
| GET | `/api/v1/documents` | Patient-scoped list, filters and pagination |
| GET | `/api/v1/documents/:id` | Patient-scoped metadata |
| PATCH | `/api/v1/documents/:id` | JSON containing permitted metadata fields only |
| GET | `/api/v1/documents/:id/download` | Owner-authorized, short-lived attachment URL |

Example upload using a synthetic file and a token obtained through the existing login endpoint:

```sh
curl http://localhost:5000/api/v1/documents \
  -H "Authorization: Bearer $PATIENT_TOKEN" \
  -F 'file=@./synthetic-report.pdf;type=application/pdf' \
  -F 'category=lab_report' \
  -F 'hospital_name=Synthetic Hospital' \
  -F 'document_date=2026-01-10'
```

Successful upload/detail/PATCH response shape (synthetic values):

```json
{
  "success": true,
  "document": {
    "id": "00000000-0000-4000-8000-000000000001",
    "original_filename": "synthetic-report.pdf",
    "file_type": "pdf",
    "category": "lab_report",
    "hospital_name": "Synthetic Hospital",
    "document_date": "2026-01-10",
    "uploaded_at": "2026-10-20T08:00:00.000Z",
    "processing_status": "processing",
    "sort_date": "2026-01-10",
    "sort_date_source": "document_date"
  }
}
```

List example: `GET /api/v1/documents?category=lab_report&hospital=Synthetic%20Hospital&uploaded_from=2026-01-01&uploaded_to=2026-12-31&limit=20&offset=0`. Response: `{ "success": true, "documents": [ ... ], "pagination": { "limit": 20, "offset": 0, "has_more": false } }`.

Filters combine with AND. Hospital matching is exact and case-insensitive. Upload date boundaries are inclusive UTC calendar dates; they filter upload time, not clinical document date. Dates must be real `YYYY-MM-DD` values. Pagination defaults to 20/0, permits limit 1–100 and offset 0–10000, and rejects duplicated, unknown or malformed parameters. Ordering is document date descending, falling back to the UTC upload date, then upload timestamp descending and UUID ascending. `sort_date_source` explicitly distinguishes the upload fallback. Offset pagination is deterministic for an unchanged result set; concurrent inserts or edits can move page boundaries.

PATCH example: `{"category":"prescription","hospital_name":"Synthetic Clinic","document_date":null}`. At least one permitted field is required. Hospital names are trimmed, 1–120 Unicode characters, without control characters. Document dates cannot be in the future; JSON null clears an unknown date. Multipart uploads omit an unknown date rather than sending an empty or null string. Unknown fields, `patient_id`, storage fields, status and timestamps are rejected.

Download response: `{"success":true,"download_url":"<short-lived HTTPS S3 URL>","expires_in":60}`. Treat the complete URL as a bearer secret; do not log it or put it in analytics. A standard SigV4 URL contains a signer credential identifier, signature and possibly a temporary session token as required by AWS; it does not contain the secret access key. It reveals the opaque object path and bucket hostname to the authorized downloader. It is never stored as a public URL in PostgreSQL. Expiry limits new access, not bytes already downloaded or an already-started transfer. Existing issued links are not revoked by changing metadata.

Errors have the existing `{ "success": false, "error": { "code": "...", "message": "..." } }` envelope. Missing/invalid JWT: 401. Missing and foreign documents: identical 404. Invalid fields or multipart/interruption: 400. Size overflow: 413. Unsupported extension/MIME: 415. Invalid content or validation budget: 422. Upload rate limit: 429. Busy, disabled or unavailable storage/database upload: controlled 503. No raw driver, parser, AWS or file-content diagnostics are returned.

## Validation and resource limits

Busboy streams one file to a random private temporary directory (0700), file mode 0600, computing SHA-256 while writing. Paths are generated internally. Filenames are reduced to a basename, normalized, stripped of unsafe/control/bidirectional characters, and capped at 240 UTF-8 bytes; filenames are metadata only. Extension, canonical MIME and content must agree. Multipart fields, part counts, lengths and total request overhead are bounded; empty, duplicate, unknown, malformed and truncated uploads fail before S3.

A separate worker validates the bounded file. Sharp fully decodes single-frame PNG/JPEG with pixel limits and strict corruption handling. PDF.js parses the document and page operator lists with page/operator limits; signatures, EOF and cross-reference integrity are checked. Encrypted PDFs, catalog/page JavaScript actions and embedded attachments are rejected. No PDF text extraction API or OCR is called. Worker output and parser diagnostics are discarded. Original bytes are never rewritten.

Workers have a 128 MiB old-generation/16 MiB young-generation JavaScript heap budget, a validation deadline and termination on abort. Development uses Node 24's native TypeScript stripping for the standalone worker, without inherited tsx instrumentation; production uses emitted JavaScript. Native library and external buffers are outside the V8 heap quota. File/pixel/page/concurrency limits constrain them, but this is not a hard operating-system memory sandbox or a malware/virus-free guarantee. Production needs process/container quotas, decoder dependency patching and an approved malware scanning/isolation policy.

Temporary files are removed on normal success, validation/storage/DB failure and request interruption. A process crash can leave local temporary files; a deployment must provide safe age-based cleanup and private encrypted ephemeral storage. No raw medical contents or metadata are logged.

The upload deadline stops file intake, validation and S3 work. Database operations use the existing pool timeouts (3-second statement/5-second query timeout); cleanup uses independent deadlines so disconnects do not cancel compensation. Consequently the full request/cleanup can outlast the upload intake deadline. Rate limiting and admission are in memory per application instance. Trust proxy remains disabled; spoofed forwarded-IP headers cannot bypass the limit. Production proxy/distributed admission, persistent rate limits, per-patient storage quotas and authenticated bandwidth controls require deployment decisions.

## Private S3 architecture and AWS setup

No AWS resources, IAM policies, keys, bucket settings or paid services were created or changed. No actual patient files were sent to AWS. Live AWS integration is **not verified**: the current runtime configuration has storage disabled and lacks an approved S3 target. SDK behavior is verified with mocked command transport and presigner; API tests use fake storage.

Before enabling, an authorized operator must supply an existing dedicated general-purpose bucket in the configured region, verify the expected account, require TLS, configure all four Block Public Access flags at both bucket and account levels, enforce `BucketOwnerEnforced` object ownership (ACLs disabled), and set matching default SSE-S3 or approved SSE-KMS encryption. Account-level controls must be checked by the operator; this adapter verifies bucket controls and does not query S3 Control account settings. No public bucket policy should be added. These are deployment prerequisites, not infrastructure provisioned by this phase. See [AWS Block Public Access](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html).

Use workload IAM roles/the SDK default credential provider chain, or an approved local AWS profile for development; do not copy access keys into source or API requests. The adapter rejects custom AWS endpoints and does not enable acceleration or access points. It uses a fixed bucket/prefix and expected owner on requests. Keys are `<generic-prefix><random-v4-UUID>.<extension>`, independent of record and patient IDs. All references are validated before SDK use. Upload uses explicit encryption, checksum, content length/type, no ACL, private cache headers and conditional `If-None-Match: *` to prevent overwrite. Private bucket checks run before each upload/download and fail closed.

Required least-privilege runtime IAM actions:

| Resource | Actions | Purpose |
| --- | --- | --- |
| `arn:aws:s3:::APPROVED_BUCKET` | `s3:GetBucketPublicAccessBlock`, `s3:GetBucketPolicyStatus`, `s3:GetBucketOwnershipControls`, `s3:GetEncryptionConfiguration` | Read privacy/encryption controls |
| `arn:aws:s3:::APPROVED_BUCKET/medical-documents/*` (use configured prefix) | `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject` | Upload, HEAD/GET/presigning, compensation of new unlinked originals |
| Same object resource, if versioning is enabled | `s3:GetObjectVersion`, `s3:DeleteObjectVersion` | Version-bound download and compensation |
| Approved KMS key ARN, only for SSE-KMS | `kms:GenerateDataKey`, `kms:Decrypt` with an appropriate key policy | Upload checksum/encryption and retrieval |

Constrain KMS use to the approved regional S3 service and applicable encryption context, accounting for whether S3 Bucket Keys are enabled. Scope all object permissions to the exact configured bucket/prefix; do not grant wildcard S3 administration, bucket creation, public-policy/ACL writes or migration credentials to the runtime. IAM cannot express patient ownership through this shared prefix: the API's scoped PostgreSQL lookups provide patient isolation. Restrict independent writers to this application prefix and review IAM/bucket/KMS policies before enabling. No runtime ListBucket permission is needed for normal operations; a missing object may produce 403 instead of 404 without it, leading to conservative reconciliation rather than an unsafe cleanup assumption. A separate operator role may need inventory/list permissions for reconciliation. IAM action names are documented in [AWS S3 permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html) and [GetBucketEncryption](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketEncryption.html).

Download first selects by both record UUID and JWT patient ID, validates the private reference, rechecks bucket controls and HEAD-verifies object size/type/encryption. It signs a version-specific GET where available, forcing attachment disposition with a safe ASCII fallback and encoded filename, canonical content type and private/no-store cache behavior. URL protocol, AWS regional bucket hostname and object path are checked. See [AWS presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html). Enabling AWS remains a separate authorized operator task; no live results are claimed here.

## Consistency, compensation and remaining risks

1. Parse/validate locally before S3. Validation failures create no database row or object.
2. Upload original to S3, then insert metadata using the restricted runtime role. Never acknowledge success before both operations complete. SQL uses parameters and every lookup/update is scoped to the JWT patient.
3. S3 failure before a write produces 503 without a DB insert. A possibly completed write triggers compensation. A conditional collision/conflict never authorizes deleting a preexisting object.
4. After S3 succeeds, an aborted request before insertion compensates the object. If insertion throws, read back the generated record ID for the same patient: a matching stored reference confirms commit and preserves the original; a confirmed absent/nonmatching row permits compensation. If read-back also fails, preserve the private object and report 503 for operator reconciliation rather than risk deleting a committed original.
5. Cleanup is attempted at most twice, each with an independent 10-second adapter deadline; SDK requests allow at most two attempts. Exact returned S3 versions are deleted, avoiding a versioned delete marker that retains the original. If the PUT acknowledgement was lost, HEAD discovers the current version before cleanup. Object Lock, permissions, version changes, transport failures or process crashes may prevent cleanup. A generic reconciliation warning contains no object key, patient identity, medical metadata or underlying error.
6. Disconnect after a committed insert preserves both the record and original; the patient can recover through list/detail. There is no upload idempotency key, so retrying an unknown result can create a duplicate record.

S3/PostgreSQL are not one transaction. A process crash between storage and insert, repeated cleanup failure, or unavailable DB read-back can leave a private unlinked object. No durable reconciliation queue or automatic sweeper was added. Before production, define an approved inventory-vs-database reconciliation process with an age grace period and explicit recheck of references/versions; use an operator role and avoid bulk deletion. Logs intentionally omit identifiers, so reconciliation needs controlled storage inventory and DB access. Do not claim zero orphan risk. A durable workflow/outbox, retention/consent, audit history, account-level control evidence, malware policy, encrypted temporary storage, storage quotas and monitoring remain production decisions. No destructive deletion of linked medical records is implemented.
